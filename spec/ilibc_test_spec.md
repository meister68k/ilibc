## 2. 試験方針

| # | 方針 |
|---|---|
| P1 | **試験の難所は、試験対象を使えないこと**。ハーネスは、試験対象（ilibc）の関数に依存せずに、結果を出力し、判定する（第5.6節） |
| P2 | **コンパイル時に済ませられるものは、コンパイル時に試験する**。`constexpr`の関数は、`static_assert`で検証する。コンパイルが通れば合格で、実行環境も出力手段も要らない |
| P3 | **同じ試験を、複数の環境で実行する**。コンパイル時、ホスト、エミュレータ（複数のCPU）、実機で、同一のベクタと試験本体を使う（第5.2節） |
| P4 | **期待値は、実装から独立に作る**。実装と同じ式を、試験にもう一度書くだけでは、誤りを検出できない（第6章） |
| P5 | **ホストのlibcを、第2の正解として使う**。ただし、規格上の差異は、既知の差異表（第5.7節）に従う |
| P6 | **成果物を検査する**。動作だけでなく、リンク結果に、不要なシンボル、静的初期化、C++ランタイム依存が混入していないことを確認する |
| P7 | **ツールチェーンを疑う**。コンパイラの挙動（最適化によるループの置き換え、定数評価、asmラベル等）に依存する設計は、ツールチェーン試験（TC-TL）で、事前に確認する |
| P8 | **試験は決定的**。乱数は、シード固定とし、シードをログに残す。失敗は、再現できる情報（TC ID、入力、期待値、実測値、シード）を出す |
| P9 | **未実施を許さない**。仕様書で定義した全TC IDが、必須のジョブで実施されたことを、機械的に確認する（第11.2節） |

## 3. 試験の種別と環境

### 3.1 試験の種別

| 記号 | 種別 | 内容 | 判定 |
|---|---|---|---|
| S | コンパイル時 | `static_assert`による検証 | コンパイルの成否 |
| F | コンパイル失敗 | あるコードが、コンパイルエラーになることの検証 | コンパイルの失敗と、診断の内容 |
| B | ビルド | コンパイル・リンクが通ること（結果の検査なし） | ビルドの成否 |
| P | 静的検査 | プリプロセッサ出力、AST、依存関係の検査 | 検査スクリプトの結果 |
| R | 実行時 | ターゲット（エミュレータ、実機）またはホストでの実行 | 失敗数、終了コード |
| H | ホスト差分 | ホストlibcとの比較、サニタイザ、カバレッジ | 失敗数 |
| A | 成果物検査 | `nm`、`objdump`、`readelf`、`size`による、オブジェクトとリンク結果の検査 | 検査スクリプトの結果 |
| L | リンク検査 | サンプルプログラムのリンクと、未解決シンボルの検査 | リンクの成否と、シンボル集合 |
| M | 計測・記録 | サイズ、スタック使用量、ツールチェーンの挙動の記録 | 記録（基準値の比較は、警告または情報） |

### 3.2 試験環境

| ID | 環境 | 用途 |
|---|---|---|
| E1 | **ホスト**: x86 Linux、**`-m32`でILP32にビルド**（ホストlibcは32ビット版）。符号付き`char`が既定 | S、F、B、P、H、A、L。サニタイザ、カバレッジ、実行時（R）も可 |
| E2 | **ARM Cortex-M3**（エミュレータ。`arm-none-eabi`ツールチェーン、セミホスティング）。`char`は符号なしが既定 | R。除算命令あり |
| E3 | **ARM Cortex-M0**（エミュレータ） | R。**除算命令なし**（コンパイラ実行時ライブラリの除算関数への依存を検証する。概要仕様書 第10.5節） |
| E4 | **RISC-V RV32IMC**（エミュレータ、セミホスティング） | R。第2の命令セット |
| E5 | 実機（任意） | リリース前のR |

- E1は、`-m32`を必須とする。ilibcは、ILIBC前提の`static_assert`（`int`と`long`が32ビット）を持つため、64ビットのままではビルドできない。32ビットのホストlibcをオラクルとすることで、`long`の範囲もilibcと一致する（`strtol`の差分試験が成立する）。**64ビット環境では、TC-GN-10の「ILP32でないとビルドエラー」だけを行う**（D-T1）。
- エミュレータの具体的な機種は、D-T2で決める（候補: QEMUの`mps2-an385`、`virt`）。
- **`char`の符号**: E1（符号付き）とE2〜E4（符号なし）で、両方を既定で網羅する。さらに、TC-GN-10で、各環境の既定の逆を指定して実行する。

### 3.3 コンパイラ・言語水準・最適化

| 項目 | 値 |
|---|---|
| コンパイラ | GCC（最新の安定版と、その直前の版）、Clang（同）。具体的な版は、固定して記録する（D-T6） |
| 言語水準 | `-std=c++20`、`-std=c++23`（ヘッダは、C++20以上で動く。ILIBC-HDR-001 第3.2節）。試験コードはC++23で書いてよいが、実行時ハーネスは、フリースタンディングでコンパイルできること |
| 最適化 | `-O0`、`-Os`、`-O2`、`-O3`。サニタイザは`-O1` |
| 共通オプション | 概要仕様書 第2.3節（`-ffreestanding -fno-builtin -fno-exceptions -fno-rtti`等）。試験の補助として、コンパイル時の評価上限（Clang: `-fconstexpr-steps`、GCC: `-fconstexpr-ops-limit`）を、必要に応じて引き上げる（第5.3節） |

## 4. 試験の実行順序とゲート

前段が失敗した場合、後段を実行しない（原因の切り分けのため）。

| 段階 | 内容 | 失敗時 |
|---|---|---|
| 0 | **ツールチェーン試験**（TC-TL。第8.2節）。ビルド環境ごとに、1回 | 以降を実行しない。コンパイラ・設定を見直す |
| 1 | **ブートストラップ**（`mem*`の最小検査。第5.8節）。各ターゲットの実行時試験の先頭 | 終了コード2で停止。以降の実行時試験を行わない |
| 2 | **ヘッダ・ビルド試験**（TC-HD、TC-GN-01、TC-GN-03、TC-GN-04） | 以降を実行しない |
| 3 | **コンパイル時試験**（S）、**コンパイル失敗試験**（F） | 失敗を記録して、以降も続行 |
| 4 | **ホスト差分・サニタイザ・カバレッジ**（H） | 同上 |
| 5 | **ターゲット実行**（R）。E2→E3→E4（→E5） | 同上 |
| 6 | **成果物・リンク検査**（A、L） | 同上 |
| 7 | **計測・記録**（M）、**変異試験**（TC-GN-09） | 情報として記録 |

## 5. 試験基盤

### 5.1 ディレクトリ構成

```
test/
  common/
    vectors/        # 試験ベクタ（ctypeの区間、文字列関数の事例、strtolの事例ほか）
    oracle/         # 実装から独立した参照（strtolの参照パーサ、基数変換、モデル関数）
    harness/        # CHECKマクロ、ミニ乱数、出力関数（ilibcに依存しない）
  constexpr/        # [S] static_assert試験
  compilefail/      # [F] 失敗試験（失敗用と、対になる対照用）
  host/             # [H] ホスト差分、サニタイザ、カバレッジ
  target/
    platform/       # E2〜E4ごとの、起動コード、リンカスクリプト、セミホスティング出力
    cases/          # [R] 実行時試験（共通ベクタを使う）
    oneshot/        # フック呼び出しなど、1ケース1実行ファイルの試験
  artifact/         # [A] 検査スクリプト
  link/             # [L] サンプルプログラム
  toolchain/        # [TL] ツールチェーン試験
  ci/               # ジョブ定義、マトリクス、トレーサビリティ検査
```

### 5.2 単一ソースの原則と共通ベクタ

同じ試験の内容を、コンパイル時と実行時の両方で使う。**試験本体は1つ**にし、「引数を渡す方法」だけを差し替える。

```cpp
// test/common/ctype_cases.hpp  (excerpt)
namespace t = ILIBC_NS;       // std (freestanding build) or ilibc_under_test (host-test build)

struct Direct {               // compile time: pass the value as is
    constexpr int operator()(int x) const { return x; }
};
struct Opaque {               // run time: hide the value from the optimizer
    int operator()(int x) const { volatile int v = x; return v; }
};

template <class Id>
constexpr int ctype_first_failure(Id id) {     // -1 on success, otherwise the first failing value
    for (int c = -1; c < 256; ++c) {
        if (t::isdigit(id(c)) != ref::is_digit(c)) { return c; }
    }
    return -1;
}

// compile time (test/constexpr):  static_assert(ctype_first_failure(Direct{}) == -1);
// run time     (test/target):     CHECK_EQ(ctype_first_failure(Opaque{}), -1);
```

| 規則 | 内容 |
|---|---|
| T1 | 試験コードは、`ILIBC_NS`の別名（`t`等）で、試験対象の名前空間を指す。フリースタンディングのビルドでは`std`、ホスト差分では`ilibc_under_test` |
| T2 | 試験本体は、`constexpr`のテンプレート関数として書き、失敗した最初の入力（または-1）を返す。コンパイル時は`static_assert(... == -1)`、実行時は`CHECK`で使う |
| T3 | 実行時は、`Opaque`により引数を`volatile`経由にして、コンパイル時の畳み込みを避ける。最適化で、試験が消えないようにする |
| T4 | 試験ベクタ（入力と期待値の表）は、`vectors/`の`constexpr`配列に置き、全環境で共有する |
| T5 | エラー出力用の関数は、試験本体に含めない（`constexpr`にできるようにするため）。失敗した最初の入力を返して、呼び出し側が出力する |
| T6 | 試験でも、`errno`関連は`ILIBC_ERRNO`、`ILIBC_ERANGE`、`ILIBC_EDOM`を使う（ホスト差分のとき、公開マクロが定義されないため。ILIBC-HDR-001 第5.2節） |

### 5.3 コンパイル時試験（S）

| 項目 | 内容 |
|---|---|
| 書き方 | `static_assert(...)`。関数ごと（または関数群ごと）に、別の`static_assert`にして、失敗箇所を絞る |
| 診断 | 比較式の`static_assert`は、GCC、Clangとも、評価した値を診断に出す（例: `(5 == -1)`）。失敗した最初の入力が分かるよう、`first_failure() == -1`の形で書く |
| 評価上限 | コンパイラは、定数式の評価に上限を持つ（Clang: ステップ数。GCC: 演算数、ループ回数）。全257値の検査はほとんどの場合、既定で通るが、通らない場合は、(a)検査を関数ごと・範囲ごとに分割する。(b)試験用ビルドに限り、上限を引き上げる。TC-TL-06が、既定で足りているかを記録する |
| 外部への出力 | ない（コンパイルの成否のみ） |
| 環境 | E1（ホスト。コンパイルできれば足りる）。ただし、**E2〜E4のコンパイラでも、同じコンパイルを行う**（ツールチェーン間の差を検出する。TC-GN-01） |

### 5.4 コンパイル失敗試験（F）

「このコードがコンパイルエラーになる」ことを検査する。**別の理由（試験コードの誤り）でエラーになっても合格にならない**よう、失敗用と対照用を対にする。

```cpp
// test/compilefail/cf_cstdlib_strtol_range.cpp
// EXPECT-GCC:   not a constant expression|non-constant|modification of|read-only
// EXPECT-CLANG: not an integral constant expression|constant expression|modification
#include <cstdlib>
#ifdef CF_FAIL
static_assert(ILIBC_NS::strtol("2147483648", nullptr, 10) == 0);        // out of range: writes errno
#else
static_assert(ILIBC_NS::strtol("2147483647", nullptr, 10) == 2147483647L);   // control: compiles
#endif
```

| 手順 | 内容 |
|---|---|
| 1 | `-DCF_CONTROL`（`CF_FAIL`未定義）でコンパイルし、**成功**すること（試験コード自体が正しいことの確認） |
| 2 | `-DCF_FAIL`でコンパイルし、**失敗**すること |
| 3 | 失敗時の診断に、`EXPECT-GCC`／`EXPECT-CLANG`の正規表現のいずれかがマッチすること（コンパイラごと） |
| 4 | `#error`のスタブ、`static_assert`のメッセージは、`ilibc:`の接頭辞で判定する |

実行は、スクリプト（`ci/run_compilefail.py`）が、各ファイルを、各コンパイラ・各言語水準で行う。診断の文言は、コンパイラの版で変わるため、正規表現は緩く書き、ずれたら更新する（D-T6）。

### 5.5 成果物検査（A）とリンク検査（L）

検査は、`test/artifact/`のスクリプトで行う。対象は、E1〜E4それぞれでビルドした、`ilibc.a`、`ilibc_hooks.a`、サンプルプログラムのリンク結果。

| ID | 検査 | 方法 |
|---|---|---|
| A1 | **`ilibc.a`が定義するグローバルシンボルが、`memcpy`、`memmove`、`memcmp`、`memchr`、`memset`の5個だけ** | `nm --defined-only -g`の出力と、期待集合の完全一致（弱シンボルも不可） |
| A2 | 各オブジェクトに、未解決シンボルがない | 各オブジェクトの`nm -u`が空（`ILIBC_DEBUG`ビルドは、`__ilibc_assert_fail`のみ許す） |
| A3 | **`mem*`の関数本体に、5個の`mem*`への呼び出しがない（自己再帰を含む）** | **`nm -u`では、同じオブジェクト内の自己呼び出しを検出できない**。(a)`objdump -dr`で、各`mem*`関数の命令列から、分岐・呼び出し命令（ARM: `bl`、`blx`、`b`、RISC-V: `jal`、`call`、`tail`、x86: `call`、`jmp`）の宛先、および再配置で参照するシンボルが、`mem*`の5個のいずれでもないこと。(b)関数ごとにセクションを分けるビルド（`-ffunction-sections`）で行う |
| A4 | C++ランタイム依存がない | `nm`の出力に、`__cxa_`、`_Unwind_`、`__gxx_personality`、`_Znw`、`_Zna`、`_ZdlPv`、`_ZTV`、`_ZTI`、`_ZTS`がない |
| A5 | 静的初期化がない | `readelf -S`で、`.init_array`、`.fini_array`、`.ctors`、`.dtors`が、ないか、サイズ0。`__cxa_guard_`がない |
| A6 | データ領域の消費が最小 | サンプルプログラムのリンク結果で、ilibc由来のシンボルのうち、書き込み可能なデータは、`ilibc::detail::g_errno`の4バイトのみ（`errno`を使うとき）。`.rodata`に、`<cctype>`由来の定数データがない |
| A7 | `ilibc_hooks.a`の内容 | 定義するシンボルが、弱シンボル`__ilibc_assert_fail`のみ |
| A8 | `g_errno`の一意性 | 2つの翻訳単位が`errno`を使ってリンクしたとき、`g_errno`が、1つの弱シンボル（サイズ4）に統合される |
| L1 | 利用者側のリンク（`ilibc.a`なし） | サンプルを`ilibc.a`なしでリンクしたとき、未解決シンボルが、`mem*`の5個の部分集合に限られる（それ以外の関数呼び出しが、リンク時に残らない） |
| L2 | 利用者側のリンク（`ilibc.a`あり） | 未解決シンボルが0（コンパイラ実行時ライブラリの関数を除く。E3は`-lgcc`が必要） |

### 5.6 実行時ハーネス（R）

#### 5.6.1 構成と独立性

| 規則 | 内容 |
|---|---|
| R1 | **ハーネスは、ilibcの関数を使わない**。出力、整数の文字列化、乱数、比較は、`test/common/harness/`の、独自の最小実装で行う（名前は`th_`で始め、試験対象と衝突させない）。`printf`、`<string>`等も使わない |
| R2 | 例外、RTTI、ヒープを使わない |
| R3 | ハーネスのコンパイルにも、`-ffreestanding -fno-builtin`を指定する。ただし、コンパイラは暗黙に`mem*`を呼ぶことがあり、その実体は**試験対象のilibc**である。この循環を、ブートストラップ（第5.8節）で解消する |
| R4 | 大きな配列の集成体初期化や構造体コピーは、`mem*`を呼ばれる原因になる。ブートストラップより前では使わない |

#### 5.6.2 プラットフォーム層

環境ごとに、次の関数を実装する（`test/target/platform/`）。

```cpp
extern "C" void ilibc_test_putc(char c);                 // 1文字の出力（セミホスティング、UART、ホストではstdio）
[[noreturn]] extern "C" void ilibc_test_exit(int status); // 終了（0=成功）
extern "C" unsigned ilibc_test_stack_used();             // スタックの使用量の測定（TC-GN-06）
```

| 環境 | 出力・終了 |
|---|---|
| E1 | `stdio`、`exit` |
| E2、E3 | ARMのセミホスティング（`SYS_WRITEC`、`SYS_EXIT`系）。エミュレータの終了コードに反映する |
| E4 | RISC-Vのセミホスティング。同上 |
| E5 | UART（または、デバッガ）。結果は、LED、終了状態の変数でも示せる |

#### 5.6.3 出力形式と終了コード

```
TC-ST-07 PASS
TC-ST-08 FAIL strncpy.cpp:41 case=17 in=[61 62 00] expected=[..] actual=[..] seed=0x1234abcd
SUMMARY pass=14 fail=1 info=2
```

| 終了コード | 意味 |
|---|---|
| 0 | 全試験が成功 |
| 1 | 試験の失敗あり |
| 2 | **ブートストラップの失敗**（`mem*`が壊れている）。他の試験は実行していない |
| 3 | ハーネス自体の異常（内部エラー） |
| 42 | `oneshot`の試験で、**期待どおりに**`__ilibc_assert_fail`が呼ばれた（第5.6.4項） |

#### 5.6.4 1ケース1実行ファイル（`oneshot`）

`__ilibc_assert_fail`は戻ってはならない。そのため、「フックが呼ばれること」を検査する試験は、1ケースごとに、別の実行ファイルにする（TC-HD-07、TC-ST-17、TC-HD-16）。

| 項目 | 内容 |
|---|---|
| フック | 試験用のフックが、式のテキスト、ファイル名、行番号を出力し、終了コード42で終わる |
| 判定 | 実行ファイルの出力と終了コードを、期待と照合する。呼ばれないはずのケースは、呼ばれずに正常終了（0）すること |

### 5.7 ホスト差分（H）

#### 5.7.1 ビルドと実行

| 項目 | 内容 |
|---|---|
| ビルド | `-m32`、`-DILIBC_HOST_TEST`。ilibcの関数は`ilibc_under_test`名前空間に宣言・定義される（ILIBC-HDR-001 第3.4節）。公開マクロ（`errno`、`ERANGE`等）は定義されないため、ホストのlibcのヘッダと、同一の翻訳単位で併用できる |
| オラクル | ホストのlibc（`::strlen`等）。`setlocale(LC_ALL, "C")`を設定する。`-U_FORTIFY_SOURCE`を指定する（検査付きの置き換えを避ける） |
| 入力の生成 | ハーネス独自の乱数（xorshift32）。シードは、コマンドラインで指定し、ログに出す。PRジョブは固定、夜間ジョブは日付由来（D-T8） |
| サニタイザ | `-fsanitize=address,undefined -O1 -g`（TC-ST-10、TC-SL-13）。未初期化読み出しは、ホストが対応する構成で、`valgrind`またはMSanを使う（TC-GN-05） |
| カバレッジ | GCCの`--coverage`と`gcov`（第7.2節） |

#### 5.7.2 ホストとの既知の差異と比較規則

| # | 対象 | ホストの挙動 | 比較規則 |
|---|---|---|---|
| 1 | `memcmp`、`strcmp`、`strncmp`の戻り値 | 符号以外の値が、ilibcと異なる | **符号のみ**を比較 |
| 2 | `memchr`、`strchr`等の戻り値 | ポインタ | 先頭からの**オフセット**（または`nullptr`）を比較 |
| 3 | `<cctype>`の分類関数の戻り値 | 0または非0の`int` | `bool`と、ホストの`!= 0`を比較 |
| 4 | `<cctype>`の領域外入力（−1〜255の外） | 未定義 | **比較しない** |
| 5 | `strtol`の無効な基数 | `EINVAL`を設定して0を返す | **除外**（ilibcはエラー報告をしない。ILIBC-STL-001 D-L1） |
| 6 | `atoi`、`atol`の`errno` | `errno`を設定しない | オラクルは、ホストの`strtol(s, nullptr, 10)`（`errno`を含む）とする |
| 7 | `strtol`の`0b`接頭辞 | 新しいglibcでは、C23対応により、基数0または2のとき`0b`／`0B`を2進数の接頭辞として扱うことがある（ilibcはC89の動作） | 基数0または2で、`0b`／`0B`（符号・空白の後）の直後が`0`または`1`である入力は**比較から除外**する。ホストのlibcの版を、ログに記録する |
| 8 | ホストのlibcの版 | 版により、上記以外の差が出うる | 差が見つかったら、本表に追記して、規格（C89）で裁定する |
| 9 | `_itoa_s` | ホストのlibcに存在しない（非標準） | オラクルは、ホストの`snprintf`（基数8、10、16。`%o`、`%d`、`%x`）、実装から独立に書いた参照（全基数）、および`strtol`／`strtoul`による往復（TC-SL-23） |

### 5.8 ブートストラップ

コンパイラは、集成体のコピーや初期化で、暗黙に`memcpy`、`memset`を呼ぶ。つまり、ハーネスは、**試験対象の`mem*`が正しいことを、前提に動く**。これを崩さないため、実行時試験の先頭で、`mem*`を最小限に検査する。

| 項目 | 内容 |
|---|---|
| 内容 | `memcpy`、`memmove`、`memset`、`memcmp`、`memchr`を、短い固定のデータ（8〜16バイト）で呼び、結果を、`volatile`のスカラー変数のループ（ライブラリを使わない）で照合する。集成体初期化を使わず、データは1バイトずつ設定する |
| 失敗時 | `BOOTSTRAP FAIL`を出力し、終了コード2で停止する。以降の実行時試験は、実行しない |
| 位置づけ | TC-ST-08〜09等の詳細な`mem*`試験とは別。詳細な試験を、信頼できる土台の上で行うための足場 |

## 6. 期待値（参照）の独立性規則

| 対象 | 期待値の作り方 | 禁止 |
|---|---|---|
| `<cctype>`（TC-CT-01〜05） | 区間表（ILIBC-CTP-001 第3.2節）の各クラスを、**文字列リテラルの走査**（例: 大文字は`"ABCDEFGHIJKLMNOPQRSTUVWXYZ"`に含まれるか）で作る。個数は、定数として別に持つ | 実装と同じ範囲式（`'A' <= c && c <= 'Z'`の変形）を、試験に書くこと |
| `<cstring>`（TC-ST-01〜03） | **手書きの期待値**（入力と期待結果の対）。「試験の重点」（ILIBC-STR-001 第5章）の各項目を、少なくとも1ケース | 実装の出力を、期待値としてコピーすること |
| `<cstring>`（大量入力） | ホストlibc（第2の正解）。補助として、実装と**異なるアルゴリズム**のモデル関数（例: `strstr`は、全位置で全文比較する素朴なモデル） | |
| `strtol`系（TC-SL-03、08〜11） | **参照パーサ**（`test/common/oracle/`）: `unsigned long long`で桁を累積し、最後に、32ビットの範囲と比較する。境界値の文字列は、**基数変換の別実装**で、数値から生成する | 実装の「桁を足す前のオーバーフロー判定（`limit`、`last`）」方式を流用すること |
| `errno`・`err`（TC-SL-06、07） | **番兵値**（例: `errno`を12345にして、呼び出し後も12345であることで「変更しない」を確認） | |
| ホストlibc | 第5.7.2項の比較規則に従う | 無条件に正とすること |

**レビュー規則**: 試験コードのレビューで、「期待値が、実装と独立しているか」を、確認項目にする。

## 7. 網羅基準

### 7.1 機能の網羅

- 各関数仕様書の「試験の重点」の**全項目**を、少なくとも1つの試験ケースに対応させる。対応表（項目 → TC ID、ケース名）を、`test/common/vectors/`に置く。
- 境界値の標準セット: 0、1、最大、最大＋1、最小、最小−1、空、`n`=0、先頭、末尾、重なり、ちょうど`n`、`n`超、上位ビットが立ったバイト（0x80〜0xFF）。

### 7.2 コードの網羅

| 項目 | 基準 |
|---|---|
| 対象 | ilibcの全コード（ヘッダ内の`inline`関数と、`mem*`の`.cpp`）。`ilibc_hooks.a`の既定フックは除く |
| 指標 | 行カバレッジ、分岐カバレッジ |
| 目標 | **100%**（D-T7） |
| 計測方法 | E1（`-m32`、GCCの`--coverage`、`-O0`）で、実行時試験（TC-xx-07〜09、TC-ST-06〜09、TC-SL-06〜12等）を実行して測定する。**コンパイル時試験は、カバレッジを取れない**。したがって、各関数の実行時試験が、コンパイル時試験と同等の入力範囲を持つこと（TC-CT-08のように、実行時にも同じ全数検査を行う） |
| 除外 | 到達不能なコード（あれば、理由を記録）。`ILIBC_DEBUG`の失敗経路は、`ILIBC_DEBUG`ビルドの`oneshot`で網羅する |

### 7.3 変異試験（第2段階）

TC-GN-09を参照。カバレッジが100%でも、「試験が、誤りを検出できるか」は別の問題であり、変異試験で補う。

## 13. I/O拡張の試験追加（ILIBC-IO-001 v0.4）

既存のTC IDおよび既存88項目を維持したうえで、**TC-IO-01〜18の18項目**を追加する。個々の入力・合格条件はILIBC-IO-001第11章を正本とする。この時点の総管理対象は106項目（第14節まで含めると114項目）。ただし既存の88項目と追加のTC-IO項目は区別して報告する。

最優先の新しいゲートは、(a) バックエンドなしの`<ilibc/format.hpp>`がコンパイル・リンク成功、(b) バックエンドなしの`<cstdio>`は`#error`、(c) `ILIBC_IO_BACKEND_POSIX`を指定した`<cstdio>`はホスト`<unistd.h>`の`::write`へ接続、(d) `<stdio.h>`は引き続きスタブ、である。

TC-IO-08ではPOSIX `pipe/read/write`を使い、`btx_unistd.h`を取り込まない。TC-IO-09はホスト上の故障注入で部分書込み、0、負値を検証。`ILIBC_HOST_IO_TEST`はPOSIXバックエンドを選択する別名であり、既存の`ILIBC_HOST_TEST`（ホストlibc名の隔離）と分離する。

既存TC-GN-04とTC-TL-08の`<cstdio>`に関する記述は、**未選択では拒否される条件付きヘッダ**として解釈する。ヘッダ統合検査で意図しない間接`<cstdio>`の取込みを検出する方針は維持する。

## 14. 追加試験: 入力I/Oと`clear_errno`（ILIBC-IO-001 v0.5）

既存TC IDを改番せず、以下を追加する。

| ID | 試験 |
|---|---|
| TC-IO-19 | `fgets`改行保持、境界、部分行、EOF |
| TC-IO-20 | `gets`配列限定、容量自動取得、ポインタ拒否 |
| TC-IO-21 | `fgetc`/`getchar`の文字・EOF・エラー |
| TC-IO-22 | `fread`の要素数、部分読み込み、EOF |
| TC-IO-23 | err明示・省略・nullptrと成功/EOF時不変 |
| TC-IO-24 | POSIX read/pipeおよび故障注入 |
| TC-IO-25 | `clear_errno`と入力APIの結合およびホストerrno分離 |
| TC-IO-26 | I/O未選択時の`<cstdio>`拒否とformat単独リンク |
| CE-01 | `clear_errno(int&)`の型・アドレス一致と`constexpr`性 |
| CE-02 | `clear_errno()`のグローバル版とホストerrno分離 |
| CE-03 | 入力APIとの結合（`clear_errno`経由のerr渡し） |

`<cerrno>`の`clear_errno`単体試験としてCE-01〜03を追加し、型・アドレス、`constexpr`、グローバル変数の分離を検査する。定義の正本はILIBC-ERR-001 §12。

- Linuxホスト試験ではPOSIX `<unistd.h>`の`::read()`を使用する。BaTTaXのヘッダは必要としない。
- インタラクティブ入力の代わりに`pipe`と固定入力を用いて決定的に検証する。
- 1バイトreadによる次行の先読み防止、部分要素の残存、`errno`不変とクリアの区別を必ず試す。
- 既存88項目およびTC-IO-01〜18は残す。追加試験を未実装のままPASSとしない。

これで総管理対象は**114項目**（既存88＋TC-IO 26）になる。
